# 누적 실적 시스템 구현 계획

- 작성일: 2026-10-28
- 진행 상태: 준비 단계와 1단계 구현·검증 완료. 2단계 이후는 미구현이다. [준비·1단계 결과](DAY_PERFORMANCE_STAGE1.md)를 참고한다.
- 기준 기획: [날짜 진행 및 누적 실적 평가](DAY_PERFORMANCE_SPEC.md), [리메이크 구현 기준](../GAME_REMAKE_SPEC.md)

- 유지할 패키지: Input System 1.20.0, URP 17.3.0, Test Framework 1.6.0, uGUI 2.0.0

## 1. 작업 범위와 완료 조건

기존 수락·출동·랜덤 맵·주행·구출·후송을 유지하면서 일차, 누적 실적, 정기 평가, 로컬 저장, 결과 UI와 백그라운드 일시정지를 연결한다. Unity·패키지·프로젝트 설정을 변경하거나 새 패키지를 도입하지 않는다. 현재 코드와 에셋의 GUID·직렬화 필드·인스펙터 값은 필요한 부분만 수정한다.

완료 시 다음 흐름이 동작해야 한다.

```text
Start → 시작하기 → 저장 상태별 Waiting 진입
→ 미션 수락·출동 → GamePlay → 픽업 → 병원 인계
→ 결과 표시 → 확인 및 저장 성공 → 다음 일차 Waiting
→ 6·11·16일차 등에는 누적 평가를 먼저 표시
→ 통과: 계속하기 및 저장 성공 → 누적 실적 유지·다음 누적 목표 안내
→ 미달: 해고 상태 저장 → 다시 시작 및 저장 성공 → 1일차·목표 200점
```

계획의 파일명은 역할을 설명하기 위한 후보이며, 해당 역할이 기존 코드에 있으면 재사용한다. 새 C# 파일은 아래 계획대로 실제 구현을 요청받았을 때만 생성한다. 사용자 변경을 보존하며 불필요한 공용 프레임워크나 클래스 분할은 추가하지 않는다.

## 3. 단계별 구현과 검증

### 준비 단계 — 기준 상태 확보

**수정 범위:** 게임 기능은 변경하지 않는다. 관련 씬·프리팹 참조, Console, 기존 검증 소스와 실행 조건을 확인하고 결과를 기록한다.

**검증:** Unity 6000.3.23f1에서 컴파일 및 기존 출동→픽업→병원 흐름을 확인한다. 현재 소스에 있는 `VehicleImpactTests`와 `AmbulanceSteeringTests`를 우선 확인한다. `Md/MISSION_DISPATCH.md`에 기록된 `MissionDispatchFlowTests`는 현재 소스 목록에서 확인되지 않으므로 존재한다고 가정하지 않는다. 발견되는 기존 오류는 이후 변경으로 생긴 오류와 구분한다.

**완료 조건:** 현재 동작과 테스트 가용 범위가 정리되고, 기존 사용자 편집을 보존할 수정 지점이 확인된다.

### 1단계 — 실적 계산과 진행 상태

**수정 범위:** `Assets/Scripts/Missions/`에 계산·진행 상태 역할을 최소한으로 추가한다. 후보 이름은 `PerformanceRules`, `GameProgress`다. 아직 씬 흐름을 변경하지 않는다. 관련 순수 규칙 테스트는 기존 관례에 맞춰 `Assets/Scripts/Editor/`에 배치한다.

**구현 내용:**

- 실제 HP 1%당 1점, 생존 무사고 +30점, 저속 1회 -2점·고속 1회 -10점, 사망 0점.
- 하한 0을 적용하고 마지막에 한 번 정수 반올림한다. 소수 부분 0.5는 올림한다.
- HP 내림 표시·0.1% 미만·사망 표시와 실제 HP의 상태 판정을 구분한다.
- 첫 접촉의 법선 방향 상대 속도 절댓값 중 최댓값으로 40km/h 경계를 판정한다.
- 현재 일차, 누적 실적, 평가 구간 번호, 일반 진행·평가 대기·해고 상태를 관리한다. 목표는 구간 번호에서 일관되게 계산하여 일차만 보고 평가 완료 여부를 잘못 추정하지 않는다.
- `k`번째 누적 목표는 `200k + 10k(k - 1)`이다. 평가 통과 후 실적을 유지하며, 해고 후 재시작에만 플레이 기록을 초기화한다.

**검증:** EditMode에서 정상·실패·경계값을 검사한다. 예시는 HP 72.46% 무사고 102점, 72.50% 무사고 103점, HP 0은 보너스 없이 0점, HP 70·30·0 경계, 속도 40 미만·정확히 40·초과다. 누적 목표 200·420·660·920·1,200점과, 누적 250점에 170점을 추가해 420점으로 통과하는 사례를 검사한다. 같은 하루 완료·같은 평가 완료를 두 번 적용해도 결과가 중복되지 않아야 한다.

**완료 조건:** 씬이나 차량 없이도 확정 기획의 계산·진행 전환을 재현한다.

### 2단계 — 로컬 저장과 Start 진입

**수정 범위:** `Assets/Scripts/Missions/`에 진행 저장 역할을 추가하고 `StartSceneMenu.cs`, `Start.unity`에 읽기 오류·재시도 UI를 연결한다. 저장 API·데이터 형식은 실제 구현 시 기존 기능과 대상 플랫폼의 공식 문서를 확인해 선택한다. 계정·서버·기기 간 동기화는 추가하지 않는다.

**구현 내용:**

- 일차·누적 실적·평가 상태를 하나의 일관된 저장 단위로 취급한다. 차량 위치·당일 시드·미완료 환자 및 충돌 기록은 복원 대상으로 저장하지 않는다.
- 저장 후보를 준비하고 저장 성공을 확인한 뒤 현재 진행 상태와 화면 전환에 반영한다. 재시도 시 원래 상태에 같은 실적을 반복 가산하지 않는다.
- 저장 없음·정상 진행·평가 대기·해고·읽기 실패를 구분한다. 읽기 실패를 새 게임으로 처리하지 않는다.
- 기존 `시작하기` 버튼에서 읽기를 수행하고, 성공한 저장 상태만 Waiting에 전달한다. 읽기 실패 시 오류·재시도로 진입을 보류한다.
- WebGL에서는 실행 메모리에 기록한 것과 실제 재실행 후 남는 것을 구분하여, 필요한 저장 완료 조건을 확인한다. 기존 실제 저장과 분리한 검증용 데이터로 실패 조건을 재현한다.

**검증:** 실제 로컬 저장의 쓰기·읽기·재실행 복원, 저장 없음과 손상·읽기 오류 구분, 쓰기 실패 시 이전 상태 유지와 재시도 성공을 검사한다. 읽기·쓰기 실패는 최소한의 테스트용 진입점으로 재현하고 테스트를 위해 범용 저장 프레임워크를 만들지 않는다. Start UI 중복 입력이 로드·씬 진입을 반복하지 않는지 Play Mode에서 확인한다.

**완료 조건:** 진행 상태를 안전하게 저장·복원하고, 실패 시 자동 초기화나 덮어쓰기 없이 오류·재시도를 표시한다. 최종 WebGL 영속성 확인은 8단계까지 이어진다.

### 3단계 — 미션당 차량 충돌 기록

**수정 범위:** `Assets/Scripts/Missions/`에 미션 기록 역할을 추가한다. 후보 이름은 `MissionPerformance`다. `AmbulanceDriveController.cs`의 첫 접촉 연결과 `MissionController.cs`의 기록 시작·종료를 연결하고, GamePlay 구급차에 필요한 컴포넌트·참조만 추가한다.

**구현 내용:** 출동 주행 시작부터 인계까지 직접 접촉한 다른 차량을 기록한다. 픽업 전 충돌도 포함한다. 같은 차량의 지속 접촉은 1회, 분리 후 접촉은 추가 1회다. 여러 콜라이더로 같은 차량을 중복 집계하지 않는다. 첫 충격 기록과 기존 물리 응답의 실행 순서 때문에 분류값이 바뀌지 않도록 연결 위치를 검토한다. 상대 차량의 파손·연쇄 반응과 HP 피해 수치는 유지한다.

**검증:** Play Mode 물리 접촉으로 저속·고속, 픽업 전·후, 지속 접촉·분리 후 재충돌, 여러 차량 접촉을 검사한다. 다른 차량끼리의 충돌과 건물 접촉은 집계하지 않는다. 같은 접촉에서 이후 속도가 바뀌어도 분류가 바뀌지 않아야 한다. 새 출동에서는 당일 기록만 비워지고 저장된 누적 실적은 유지되어야 한다. 관련 기존 차량 충돌 테스트를 함께 실행한다.

**완료 조건:** 병원 인계 전까지 정확한 당일 저속·고속 횟수와 사고 여부를 제공한다.

### 4단계 — GamePlay 결과와 하루 완료

**수정 범위:** `MissionController.cs`, 필요한 결과 UI 역할과 `GamePlay.unity`의 기존 Canvas·안전 영역 하위 패널을 수정한다. `PatientHealth.cs`는 기존 공개 HP 읽기와 후송 상태 전환을 우선 재사용한다. 필드명·GUID·기존 UI 배치를 불필요하게 바꾸지 않는다.

**구현 내용:** 병원 도착 시 바로 Waiting으로 이동하는 처리를 결과 단계로 바꾼다. 차량 입력·HP 감소·실적 기록을 종료하고 인계 시점의 결과를 고정한다. 당일 실적과 이번 날을 더한 누적 표시값을 보여주되, 실제 진행 저장은 `확인` 입력 때 수행한다. 저장 성공 후에만 다음 일차 Waiting으로 이동하며 5의 배수 일차 종료에는 평가 대기 상태를 함께 저장한다. 실패하면 동일 결과로 재시도한다.

**검증:** 생존 무사고·저속·고속·사망 결과와 표시 형식을 검사한다. HP 0 이후에도 병원까지 운행할 수 있어야 한다. 결과를 오래 보거나 주변 차량이 움직여도 고정된 기록은 변하지 않아야 한다. `확인` 전 종료는 같은 날 재시작, 저장 성공 후 종료는 다음 날 복귀, 실패·연속 클릭은 실적·일차 중복 반영 없음으로 확인한다. 재도전 시 기존 시드 복원 대신 새 생성 절차가 호출되는지 검사하며, 우연히 같은 시드가 추첨되었다는 이유만으로 실패 처리하지 않는다.

**완료 조건:** 한 미션의 결과 확인이 정확히 하루 한 번의 누적 반영·저장·일차 진행으로 이어진다.

### 5단계 — Waiting 누적 안내·평가·해고

**수정 범위:** `WaitingMissionController.cs`, 필요한 평가 UI 역할, `Waiting.unity`를 수정한다. 기존 요청·수락·출동 승인과 페이드는 재사용한다.

**구현 내용:** 누적 실적·다음 누적 목표·부족 실적을 표시한다. 일반 상태에서만 기존 5초 요청을 시작한다. 평가 대기·통과 확인 전·해고·저장 오류 중에는 요청을 시작하지 않는다. 누적 실적이 목표와 같아도 통과한다. `계속하기`는 평가 완료·다음 목표를 한 번 저장하며 실적을 유지한다. 미달이면 해고를 저장하고, `다시 시작`은 실적·일차·목표 진행을 초기화해 1일차·목표 200점으로 저장한다.

**검증:** 6·11·16일차 진입에서 각각 누적 목표 200·420·660점을 검사한다. 초과·동점·미달, 초과 실적의 다음 평가 활용, 이미 다음 목표를 넘었어도 하루를 건너뛰지 않음을 확인한다. 평가 중 종료·통과 저장 전후 종료·해고 후 종료·재시작 저장 실패를 검사한다. 평가 대기와 평가 완료가 같은 6일차여도 재실행 시 화면·목표가 올바르고 중복 증가가 없어야 한다.

**완료 조건:** 연속 두 번 이상의 5일 평가가 실적 차감 없이 연결되고, 해고 상태가 재실행에도 유지된다.

### 6단계 — 백그라운드 일시정지

**수정 범위:** 기존 입력 포커스 처리와 연결할 최소한의 일시정지 역할을 추가한다. `AmbulanceDriveInput.cs`, `WaitingMissionController.cs`, 필요 시 게임 시간에 의존하는 실행 지점을 수정하고 각 씬의 참조를 연결한다. 신규 패키지는 사용하지 않는다.

**구현 내용:** 앱·탭 이탈 시 차량·교통·HP·컷신·요청 타이머를 중단한다. 기존 요청 대기는 실제 시간 대기 코루틴이므로 시간 배율만 변경하고 끝내지 않고, 백그라운드 시간을 제외하도록 처리한다. 포커스·일시정지 알림이 중복되거나 서로 다른 순서로 도착해도 한 알림만 보고 조기 재개하지 않는다. 복귀 시 이전 입력을 비우고 같은 상태를 이어간다. 실제 실행 종료 후에는 저장 복원 규칙을 적용한다.

**검증:** 주행·후송·컷신·요청 대기·결과·평가 화면에서 이탈과 복귀를 검사한다. 복귀 후 HP·차량 위치·충돌 횟수·타이머가 백그라운드 시간만큼 진행되거나 맵이 다시 생성되지 않아야 한다. 저장 처리·씬 전환 경계와 중복 포커스 이벤트도 확인한다. Editor의 시간 정지만으로 모바일·브라우저 백그라운드 검증을 대신하지 않는다.

**완료 조건:** 실행 세션 유지 복귀와 실제 재실행이 확정 기획대로 구분된다.

### 7단계 — 통합 자동 검증과 씬·에셋 검수

**수정 범위:** 필요한 EditMode·Play Mode 검증을 추가·보완하고, 새 UI·컴포넌트의 누락 참조만 수정한다. 기존 프리팹·패키지·주행 동작의 관련 없는 문제는 별도로 기록한다.

**검증:** 실제 씬과 버튼 연결로 `Start → 출동 → 픽업 → 후송 → 결과 → 다음 날 → 5일 평가 → 계속 → 다음 평가 → 해고 → 다시 시작`을 검사한다. 일차를 빠르게 진행시키는 테스트는 실제 완료 처리 경로를 호출하고, 저장할 누적 값을 임의로 덮어쓰는 검사와 구분한다. 이동을 단축한 자동 테스트는 실제 운전 검증으로 보고하지 않는다. UI의 한글·안전 영역·세로 화면·연속 입력·결과 패널의 버튼 연결을 확인한다. Console 오류, MissingReferenceException·NullReferenceException과 동작에 영향을 주는 경고를 기존 상태와 비교한다.

**완료 조건:** 순수 계산, 저장, 실제 씬 통합 검증의 결과를 구분해 기록하고 기획서의 완료 조건과 연결한다. 기존 문서의 과거 통과 기록은 새 기능의 증거로 사용하지 않는다.

### 8단계 — WebGL·모바일 확인과 밸런스 측정

**수정 범위:** 기존 WebGL 설정으로 빌드·실행한다. 검증 결과와 거리별 실적 측정 기록을 문서화한다. 확정 배점·목표·맵 생성 범위는 측정만으로 임의 변경하지 않는다.

**검증:** 배포를 전제로 하지 않고 접근 가능한 검증 환경에서 실제 브라우저 새로고침·종료 후 재진입, 탭 전환, 모바일 앱 전환·복귀, 로컬 저장 유지, 읽기·쓰기 실패 안내, 터치와 세로 레이아웃을 확인한다. 브라우저·기기·호스팅 조건을 기록한다. 길이·차선·교차로·교통 조건이 다른 맵에서 후송 시간·인계 HP·사고·당일 및 5일 누적 실적을 측정해 초기 목표 200점과 다음 누적 목표들의 난도를 평가한다.

**완료 조건:** 실행한 환경의 범위에서 실제 저장 영속성과 복귀 흐름을 확인하고, 밸런스 변경이 필요하면 측정 근거와 후보를 제시한다. 실행하지 못한 플랫폼·기기는 미검증으로 남긴다.

## 4. 단계 순서와 변경 경계

- 기본 순서: 준비 → 1 계산·진행 → 2 저장·Start → 3 기록 → 4 후송 결과 → 5 Waiting 평가 → 6 일시정지 → 7 통합 검증 → 8 플랫폼·밸런스.
- 각 단계에서 관련 컴파일·테스트를 먼저 확인한 뒤 다음 단계로 진행한다. 테스트는 실제 동작·실패·회귀 위험을 검증하도록 추가하고 구현 내용을 그대로 반복하는 테스트는 피한다.
- 1~3단계는 기초 역할을 준비하는 단계이며 전체 게임 기능 완료로 보고하지 않는다. 최종 완료에는 씬·프리팹 연결, 인스펙터 참조, 한글 UI 및 대상 플랫폼 검증이 포함된다.
- UI는 기존 스타일과 안전 영역을 따르는 최소 구성을 먼저 연결하고, 상세 디자인은 기능 검증 후 필요한 범위에서 다듬는다.
- 저장 API·포커스 알림·시간 처리 등 외부 사양 확인이 필요한 구현에 들어갈 때 설치 버전과 대상 플랫폼의 공식 문서를 조사한다. 이 계획 작성에서는 새 API를 선택·적용하지 않았다.

## 5. 최초 계획 작성 시점의 확인 범위

아래는 최초 계획 문서 작성 당시의 기록이다. 이후 준비·1단계 구현과 실제 검증 결과는 [별도 결과 보고](DAY_PERFORMANCE_STAGE1.md)에 구분한다.

- 기획, 기존 코드 연결 지점, 실제 프로젝트·패키지 버전, 빌드 씬 목록과 존재하는 테스트 소스를 확인했다.
- 이 문서와 기존 기획서의 계획 링크만 작성했다. C#·씬·프리팹·인스펙터·패키지·프로젝트 설정은 수정하지 않았다.
- 위 단계의 컴파일·자동 테스트·Play Mode·WebGL 빌드·모바일·밸런스 측정은 모두 향후 수행 항목이며 이번 작업에서 실행하지 않았다.
