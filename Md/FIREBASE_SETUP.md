# Firebase 게스트 로그인·최고 실적 설정

## 이번 구현

Unity 6000.3.23f1의 기존 Start → Waiting → GamePlay 흐름에 REST 통신을 연결했다. 새 패키지, 새 씬, 기존 씬 YAML, 기존 진행 저장 형식은 변경하지 않았다. 로그인 패널과 계정 카드는 기존 컨트롤러가 가진 Canvas·안전 영역·글꼴을 이용해 실행 시 생성한다. 별도의 컴포넌트 드래그 연결은 필요 없다.

| 완료 조건 | 구현 내용 | 실행 확인 |
| --- | --- | --- |
| 익명 인증·복원 | Start의 게스트 로그인, refresh token 유지·갱신, 인증 오류 안내 | 사용자 확인 필요 |
| 계정 안내 | Waiting 손님 이름·서버 최고 기록·재시도·로그아웃 | 사용자 확인 필요 |
| 확정 실적 제출 | 결과 확인에서 로컬 저장 성공한 뒤 누적 실적 제출 | 사용자 확인 필요 |
| 최고 기록 유지 | ETag 조건부 쓰기, 서버의 감소·삭제 차단 규칙, int 축소 없는 long 처리 | 사용자 확인 필요 |
| 실패·수명 처리 | UID·프로젝트에 묶인 미전송 후보 저장, 높은 후보 병합, 씬 전환 유지, 종료 시 요청 정리 | 사용자 확인 필요 |
| 초기화 보호 | 초기화할 현재 실적을 먼저 로컬 미전송 기록에 보존, 서버 완료는 기다리지 않음 | 사용자 확인 필요 |

요청에 따라 컴파일, 자동 테스트, 플레이 모드, Firebase 실제 요청, WebGL 빌드·브라우저 검증은 실행하지 않았다. 아래 설명은 구현 의도이며 실행 성공 보고가 아니다. 기존 테스트 중 인증 없이 Start·Waiting에 진입하는 테스트는 새 인증 진입 조건에 맞게 조정이 필요할 수 있다. 테스트 코드는 수정하지 않았다.

## 1. Firebase에서 직접 할 일

1. Firebase 콘솔에서 사용할 프로젝트를 선택한다. 강의 예제의 프로젝트·키를 복사하지 않는다.
2. **Authentication → Sign-in method(로그인 방법) → Anonymous(익명)** 제공업체를 활성화하고 저장한다.
3. **Realtime Database → 데이터베이스 만들기**에서 위치를 선택한다. 강의에 맞추려면 Singapore(asia-southeast1)를 선택한다. 이미 DB가 있으면 다시 만들 필요 없다. 잠금 모드로 생성한다.
4. Realtime Database의 **규칙** 탭에 이 저장소의 `Md/FIREBASE_DATABASE_RULES.json` 전체를 붙여넣고 직접 게시한다. 기존 DB에 다른 용도의 데이터·규칙이 있다면 전체를 덮어쓰지 말고 해당 프로젝트의 규칙과 병합한다.
5. Realtime Database의 **데이터** 탭에서 HTTPS 루트 주소를 복사한다. 예: `https://YOUR-PROJECT-default-rtdb.asia-southeast1.firebasedatabase.app`. Firestore 주소나 콘솔 URL이 아니다. `/scores.json`이나 `?auth=`를 덧붙이지 않는다.
6. **프로젝트 설정 → 일반**에서 **Web API Key**를 확인한다. Firebase 웹 앱 등록이 필요하면 해당 프로젝트의 웹 앱을 등록한 뒤 설정의 `apiKey`를 사용한다. 서비스 계정 비공개 키나 Database secret을 사용하지 않는다.

규칙은 `scores`의 이름·점수만 공개 읽기를 허용한다. 각 손님은 자기 UID에만 쓸 수 있고, 점수 감소·삭제·음수·소수·예상 외 필드는 거부한다. 이 규칙은 클라이언트 점수의 진위를 검증하는 서버 게임 판정이 아니다.

API Key에 기존 애플리케이션/API 제한이 있다면 사용하는 Unity Editor·WebGL 요청과 Firebase Authentication/Secure Token 요청을 허용하는지 확인한다. 오류를 피하려고 프로젝트 전체 보안을 임의로 해제하지 않는다.

## 2. Unity에서 직접 입력할 값

Project 창에서 **Assets/Resources/FirebaseSettings.asset**을 선택하고 Inspector에 다음 두 값을 입력한다.

| 필드 | 입력 값 |
| --- | --- |
| Api Key | 위에서 확인한 같은 프로젝트의 Web API Key |
| Database Url | 위에서 복사한 같은 프로젝트의 HTTPS Realtime Database 루트 주소 |

두 값은 비워 두었다. 관리자 자격 증명은 필요 없다. 에셋 이름과 Resources 위치를 유지해야 `Resources.Load`로 읽힌다. Firebase 콘솔 설정은 이 작업에서 실행하지 않았다.

## 3. 직접 확인할 실행 순서

1. **Start 씬**부터 실행한다. 설정이 없으면 안내가 나오고 시작하기는 잠긴다.
2. **게스트 로그인**을 누른다. 로그인 완료와 손님 이름이 표시된 뒤 **시작하기**를 누른다.
3. Waiting 하단에 같은 손님 이름과 서버 최고 기록·동기화 상태가 표시되는지 확인한다. 평가·브리핑·초기화 확인창 중에는 카드가 숨겨지고 계정 입력이 차단된다.
4. 정상 출동·후송 후 결과의 **확인**을 누른다. 기존 진행 저장이 성공해야 다음 날로 이동하며, 저장한 누적 실적이 `scores/{uid}/name`, `score`에 반영되는지 콘솔에서 확인한다. 서버 응답은 다음 날 이동의 필수 조건이 아니다.
5. **로그아웃 → 게스트 로그인** 후 같은 손님이 복원되는지 확인한다. 실행을 종료하고 다시 켜도 동일한 저장 환경이면 같은 UID를 사용한다.
6. 진행 초기화 뒤 누적 실적은 0이 되지만 서버 최고 기록은 유지되는지 확인한다. 낮은 새 기록은 유지, 높은 새 기록은 갱신되어야 한다.
7. 네트워크를 끊고 하루 결과를 확인한다. 로컬 저장·다음 날 이동은 유지되고 동기화 실패가 표시되어야 한다. 연결 복구 후 Waiting의 **동기화 재시도**를 누른다. 실패 중 초기화·종료한 뒤에도 같은 UID의 미전송 최고값을 재시도해야 한다.
8. 실제 WebGL은 HTTPS 배포에서 위 과정을 반복한다. `X-Firebase-ETag` 요청 헤더, `ETag` 응답 헤더, `If-Match` PUT의 브라우저 CORS 동작을 직접 확인한다. 헤더를 읽지 못하면 안전하지 않은 무조건 PUT 대신 오류를 표시한다. 별도 프록시·호스팅 설정이 필요한 환경인지는 미검증이다.
9. 초기 점수 250 → 420, 초기화 후 350 → 450 사례에서 서버 기록이 250 → 420 → 420 → 450으로 유지되는지 확인한다. 다른 UID의 쓰기, 점수 감소, 삭제, 잘못된 형식도 규칙으로 거절되는지 확인한다.

초기화 직전 인증·미전송 로컬 저장 자체가 실패하면 실적 유실을 막기 위해 초기화를 보류하고 저장 재시도를 안내한다. 일반적인 서버 통신 실패는 게임 진행을 보류하지 않는다. 인증 전에는 새 게임에 진입할 수 없다.

## 저장과 복구 범위

- 기존 진행: `ProgressStore`의 `progress-v1.json` 또는 기존 WebGL 진행 키를 유지한다.
- 인증·미전송 기록: Editor/일반 플랫폼은 `Application.persistentDataPath/firebase-v1.json`, WebGL은 같은 배포 origin의 localStorage 키 `codeblue-rush.firebase.v1`을 사용한다.
- 파일에는 refresh token이 포함된다. 저장소에 올리거나 공유하지 않는다. 이 저장은 암호화 보관이 아니다. ID token은 메모리에만 유지한다.
- 첫 적용 당시 존재하는 정상 로컬 진행은 최초로 로그인한 손님의 제출 후보로 사용한다. 서버 점수로 현재 일차나 누적 실적을 복원하지 않는다.
- 익명 계정은 같은 저장 환경의 갱신 자격에 의존한다. Editor와 브라우저는 자동으로 같은 손님이 되지 않으며, 다른 브라우저·도메인·기기의 기록도 자동으로 이어지지 않는다.
- 브라우저 데이터 삭제·토큰 파일 유실·계정 삭제 후에는 같은 UID 복원을 보장하지 않는다. 가입 직후 로컬 저장이 실패하면 같은 실행 중 자격은 보존하지만 종료 후 복원은 보장할 수 없다.
- 일시적인 인증 실패에서는 저장 자격을 삭제하지 않는다. 재시도 후에도 거부되면 콘솔의 익명 인증, API 제한, 해당 계정 상태를 확인한다. 무효 자격을 임의로 버리고 새 UID로 바꾸는 기능은 추가하지 않았다.
- 설정의 DB 주소와 저장된 프로젝트가 다르면 다른 프로젝트에 이전 기록을 올리지 않도록 읽기를 보류한다. 개발 중 프로젝트를 교체할 때에는 기존 인증·미전송 파일을 별도 보관하고 프로젝트별 저장 환경을 분리한다.
