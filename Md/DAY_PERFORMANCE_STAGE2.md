# 누적 실적 2단계 구현 결과

- 작업일: 2026-10-28
- 범위: 로컬 저장과 Start 진입만 구현했다. 3단계 이후는 진행하지 않았다.
- 환경: Windows, Unity 6000.3.23f1, Input System 1.20.0, URP 17.3.0, Test Framework 1.6.0, uGUI 2.0.0. 기존 WebGL 대상 설정을 유지했다.

## 변경 내용과 완료 조건

| 완료 조건 | 구현 및 검증 결과 |
| --- | --- |
| 저장 단위 | 버전 1 JSON에 일차·누적 정수 실적·평가 구간·진행 상태를 함께 저장한다. 차량 위치·시드·미완료 당일 기록은 저장하지 않는다. 필수 값 누락과 모순된 평가 이력을 거부한다. |
| 로컬 저장 | Editor·네이티브 실행은 `Application.persistentDataPath/progress-v1.json`에 임시 파일 쓰기·flush 후 교체한다. WebGL은 브라우저 `localStorage`의 `codeblue-rush.progress.v1` 키 하나에 전체 JSON을 저장한다. |
| 성공 후 채택 | `GameProgressSession.TrySave`는 저장 성공 후에만 현재 상태를 후보로 교체한다. 실패 시 기존 상태를 유지하고 같은 후보로 재시도한다. 실제 파일 실패·재시도와 중복 합산 방지를 검증했다. |
| 저장 없음·읽기 오류 구분 | 실제 미존재만 새 1일차를 제공한다. 빈 내용·손상·버전 불일치·접근 실패는 오류로 반환하며 덮어쓰기를 차단한다. 시작만으로 새 저장을 만들지 않는다. |
| Start 연결 | 기존 시작 버튼으로 복원 후 Waiting으로 이동한다. 실패 시 Start에 오류·재시도를 표시한다. 중복 입력, 실제 버튼 연결, 재시도 성공과 안전 영역 내 버튼 배치를 Play Mode에서 확인했다. |
| 상태별 복원 | 일반 진행은 저장된 일차의 수락 전 상태로 진입한다. 평가 대기·해고는 상태를 유지하고 Waiting의 요청·수락·출동을 차단한다. 실제 평가·해고 처리 및 다시 시작 화면은 5단계다. |
| 기존 기능 유지 | 기존 Start→Waiting→수락→출동→GamePlay→픽업→병원→Waiting 흐름을 통과했다. 이동만 단축한 자동 검증이며 실제 운전 검증은 아니다. |

`ProgressStore`는 저장 형식과 플랫폼 입출력을 맡고, `GameProgressSession`은 씬 사이의 현재 상태와 저장 성공 후 채택을 맡는다. `GameProgress.TryRestore`는 저장값의 진행 규칙을 검증한다. `Start.unity`에 오류 패널과 재시도 버튼을 직접 연결했으므로 별도 인스펙터 수동 설정은 없다. 기존 Waiting 직접 실행은 기존 요청 흐름을 유지하며, 저장 복원 검증은 Start 진입을 기준으로 한다.

당일 실적 확정·결과 화면·하루 종료 저장 호출은 4단계다. 현재 기존 미션을 완료해도 일차나 실적이 새로 저장되지는 않는다. 저장 실패의 화면 연결도 해당 호출부를 구현할 때 진행한다. 환자 HP·충돌·랜덤 맵·후송 로직과 Waiting·GamePlay 씬 에셋은 수정하지 않았다.

## 실제 검증

원본 프로젝트가 열려 있어 같은 버전의 격리 복사본을 사용했다. 실제 사용자 저장을 읽거나 수정하지 않고, 테스트 소유 임시 경로와 최소한의 읽기·쓰기 작업 주입으로 오류를 재현했다. 테스트 실행은 EditMode Test Runner이며, 씬 흐름 검사는 `EnterPlayMode`로 실제 Play Mode에 진입했다.

| 검증 | 결과 |
| --- | --- |
| `ProgressStoreTests` | 27개 통과. 상태별 실제 파일 왕복, 잘못된 데이터·이력 거부, 읽기 오류·재시도, 실제 임시 쓰기 실패 시 기존 파일 보존, 세션의 저장 성공 후 채택을 검사했다. |
| Start 실제 씬 검증 | 4개 통과. 저장 없음·중복 클릭, 손상 오류→재시도→저장된 6일차 복원, 평가 대기·해고의 요청 차단을 검사했다. 오류 표시 시 재시도 버튼의 네 모서리가 안전 영역 안에 있는지도 검사했다. |
| 프로세스 재실행 복원 | 쓰기·읽기 2개 통과. 한 Unity 프로세스에서 11일차·누적 420점·2구간 평가 대기를 저장하고 종료한 뒤, 새 Unity 프로세스에서 동일 상태를 읽었다. |
| 기존 회귀 검증 | 차량·조향 61개 중 52개 통과·9개 기존 실패. 실제 씬 조향 1개 및 기존 출동·후송 흐름 1개 통과. 총 63개 중 54개 통과·9개 기존 실패로 준비 단계와 동일하다. 실패 테스트 이름도 기존 기록과 일치한다. |
| WebGL C# 분기 | Unity 참조 및 WebGL 정의로 컴파일했다. 오류 0·경고 0. 실제 IL2CPP/WebGL 빌드는 아니다. |
| JavaScript 저장 브리지 | 실제 `.jslib`를 Node의 모의 브라우저 저장과 실행해 7개 assertion 통과. 미존재, 새 실행 컨텍스트 복원, 한글 문자열, 읽기 접근 실패, 쓰기 실패 시 기존 값 보존·복구를 확인했다. 실제 브라우저 영속성 검증은 아니다. |
| 변경 범위 | 원래 존재한 Assets·Packages·ProjectSettings의 SHA-256 비교로 Start 씬과 관련 스크립트 3개만 변경됨을 확인했다. 패키지·설정·기존 메타·Waiting·GamePlay 에셋은 보존했다. `git diff --check` 통과. |

기존 실패 9개는 교통 차량 질량에 적용된 기존 1.2배 계수와 테스트 기대값 차이에 관한 것이다. 이번 범위 밖이므로 수정하지 않았다. 오류 읽기 테스트에서 의도한 경고가 출력됐으며, 새 컴파일 오류나 참조 누락 오류는 관찰되지 않았다. 종료 로그에는 Unity의 기존 스레드 정리·디버거 포트 진단이 남아 있어 전체 로그가 무경고라고 판단하지 않는다.

영구 추가한 테스트는 `Assets/Scripts/Editor/ProgressStoreTests.cs`와 그 메타뿐이다. 삭제한 `PerformanceRulesTests.cs`와 메타는 복원하지 않았다. 씬 진입·프로세스 재실행용 테스트와 실행 XML·로그는 무시되는 `.utmp/PerformanceStage2/` 및 격리 복사본에만 둔다.

## 미검증 및 후속 확인

- 실제 WebGL 빌드의 IL2CPP 연결·페이지 종료 후 영속성·모바일 브라우저 저장 권한 및 용량 실패는 8단계에서 확인해야 한다. 현재 확인은 C# 분기 컴파일과 브리지 모의 실행까지다.
- 실제 기기에서 한글 렌더링·화면 회전·안전 영역의 육안 확인은 하지 않았다. Editor 자동 검증은 참조·문구·레이아웃 좌표를 확인했다.
- 수동 확인 시 Start의 시작하기로 기존 수락·출동·후송이 유지되는지 확인한다. 이 단계에서는 후송 완료가 일차 저장으로 이어지지 않는 것이 기대 결과다.
- 3단계 이후의 충돌 기록·결과 저장·누적 안내·평가 UI·재시작·백그라운드 일시정지는 미구현이다.

## 선택 근거

Editor 저장 경로는 [Unity Application.persistentDataPath](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Application-persistentDataPath.html)를 따른다. WebGL의 비동기 파일 시스템 동기화 대신 작은 진행 데이터의 저장 완료를 직접 확인할 수 있도록 [Web Storage 표준](https://html.spec.whatwg.org/multipage/webstorage.html#the-storage-interface)의 `localStorage.setItem`을 사용했다. 브라우저 저장은 같은 출처 범위이며 사용자 설정·삭제·용량 제한을 따른다. 접근·쓰기 예외를 성공이나 저장 없음으로 처리하지 않는다. JavaScript 문자열 전달은 [Unity 브라우저 상호 작용 예제](https://docs.unity3d.com/6000.3/Documentation/Manual/web-interacting-browser-example.html)의 `.jslib`와 문자열 메모리 전달 방식을 따른다. 공식 API 근거와 실제 WebGL 빌드 검증은 구분한다.
