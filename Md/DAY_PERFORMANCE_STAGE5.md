# 누적 실적 5단계 구현 결과

- 작업일: 2026-10-28
- 범위: Waiting 누적 안내·평가·해고·다시 시작만 구현했다. 6단계 이후는 진행하지 않았다.
- 환경: Windows, Unity 6000.3.23f1, Input System 1.20.0, URP 17.3.0, Test Framework 1.6.0, uGUI 2.0.0. 기존 프로젝트·패키지 설정을 유지했다.

## 구현과 완료 조건

| 완료 조건 | 구현·검증 결과 |
| --- | --- |
| 누적 안내 | Waiting에 현재 일차·누적 실적·다음 누적 목표·부족 실적을 표시한다. 통과 후에는 저장된 다음 목표를 표시하고 부족 실적 하한은 0이다. |
| 평가 통과 | 평가 대기에서 누적 실적이 해당 목표 이상이면 통과 화면을 표시한다. `계속하기` 전에는 요청을 시작하지 않는다. 저장 성공 후 누적 실적과 일차는 유지하고 평가 구간·목표만 한 번 올린다. |
| 해고 | 목표 미달이면 해고 후보를 먼저 저장한다. 성공해야 저장된 해고 화면과 `다시 시작`을 허용한다. 저장 실패에서는 평가 대기 원본·파일을 보존하고 동일한 해고 후보만 재시도한다. |
| 다시 시작 | 저장된 해고에서만 1일차·누적 0점·1구간·목표 200점 후보를 저장한다. 성공 후 출동 승인을 비우고 요청 번호를 초기화해 새 요청을 기다린다. 실패 시 기존 해고와 파일을 유지한다. |
| 재시도·중복 방지 | 원본·후보를 고정하고 저장 중 재진입을 차단한다. 실패용 재시도 버튼과 계속하기/다시 시작 버튼을 겹치지 않는 위치에 분리했다. 해고 저장 재시도를 연속 클릭해도 새 게임까지 자동 실행되지 않는다. |
| 요청 차단 | 평가 대기·통과 확인 전·해고·저장 실패·저장 중에는 요청 코루틴을 시작하지 않는다. 공개 브리핑·수락·거절·출동 호출에도 같은 진행 조건을 검사한다. |
| 재실행 | 통과 확인 전에는 기존 평가·목표, 저장 후에는 같은 일차의 다음 목표로 복원한다. 해고와 초기화 상태도 파일에서 그대로 복원한다. 읽기 실패·손상은 초기화하지 않고 Start로 돌아간다. |
| 기존 기능 | 일반 진행에서는 기존 요청 대기·거절·수락·출동과 GamePlay 결과 저장 흐름을 유지한다. 목표를 미리 넘어도 평가 일차나 하루를 건너뛰지 않는다. |

`WaitingMissionController`에서 기존 `GameProgress`의 평가·재시작 후보와 `GameProgressSession` 저장 경계를 재사용한다. 새 저장 형식이나 공용 저장 프레임워크는 추가하지 않았다. `Waiting.unity`의 기존 안전 영역 아래 누적 안내·평가 패널·저장 안내·주 입력·재시도 버튼을 직접 연결했다. 안내 공간을 확보하기 위해 기존 제목·상태·요청 버튼의 세로 앵커를 조정했다. 별도 인스펙터 수동 설정은 없다.

코루틴·버튼 구독은 비활성화 시 해제한다. 실패 후보를 가진 화면은 재활성화돼도 자동 재저장하지 않는다. 저장 중 컴포넌트가 비활성화된 경우에도 성공 상태를 유지하고 재활성화 때 요청 대기를 재개한다. 이 처리는 컴포넌트 수명에 관한 것이며, 6단계의 앱·탭 백그라운드 일시정지를 구현한 것은 아니다.

## 실제 검증

원본과 사용자 저장을 보호하기 위해 동일 버전의 격리 복사본에서 실행했다. EditMode Test Runner의 `EnterPlayMode`로 실제 Waiting 씬·버튼과 실제 파일 입출력을 사용했다. 쓰기 실패는 임시 파일 경로에 테스트 소유 디렉터리를 만들어 재현했고, 재진입 관찰용 래퍼는 실제 쓰기 전에 버튼을 다시 호출했다.

| 검증 | 관찰 결과 |
| --- | --- |
| Waiting 저장·UI 11개 | 모두 통과. 일반 안내와 기존 요청 흐름, 6·11·16일차 동점 통과, 초과 실적, 해고 저장, 각 저장 실패·재시도, 재진입·연속 클릭, 재활성화, 화면 배치, 손상 읽기 경로를 검사했다. |
| 목표·일차 | 6일차 200점·11일차 420점·16일차 660점으로 동점 통과했다. 계속하기 저장 후 각각 같은 일차에서 다음 목표 420·660·920점이었다. 누적 650점인 6일차도 실적을 유지하고 6일차·2구간·목표 420점으로만 진행했다. |
| 통과 쓰기 실패 | 6일차·250점·목표 200점 파일과 원본·후보를 유지했다. 두 번의 실패 후 재시도 성공에서도 목표는 420점으로 한 번만 증가했고 누적 250점은 유지됐다. |
| 해고 쓰기 실패 | 6일차·199점의 해고 저장이 실패하면 평가 대기와 기존 파일을 유지했다. 재활성화에서는 쓰기가 추가되지 않았다. 재시도 연속 클릭 성공 후에도 6일차·199점·해고에 머물고 별도 다시 시작을 눌러야 초기화됐다. |
| 초기화 쓰기 실패 | 다시 시작 저장 실패 시 해고 파일을 보존했다. 새로 읽어도 같은 해고였고, 성공한 초기화만 1일차·0점·목표 200점으로 반영됐다. |
| 요청·입력 차단 | 평가·해고·저장 오류 중 요청 코루틴과 요청·출동 버튼이 없고, 공개 메서드 직접 호출로도 출동하지 못했다. 실패 재시도 도중의 재진입도 추가 저장을 일으키지 않았다. |
| 두 번 연속 통과와 해고 | 실제 GamePlay 결과 확인·Waiting 버튼으로 5일차 누적 250점→6일차 통과→10일차 누적 420점→11일차 동점 통과→15일차 누적 420점→16일차 목표 660점 미달·해고→다시 시작을 연결한 검증 1개가 통과했다. 초기화 후 새 출동의 HP 100%·충돌 0회·픽업 전 상태도 확인했다. |
| 프로세스 재실행 | 실제 UI로 평가 확인 전·통과 후·해고·초기화 파일을 준비한 뒤 Unity를 종료했다. 새 Unity 프로세스에서 6일차·250점·목표 200점 평가 대기, 6일차·250점·목표 420점 일반 진행, 6일차·199점 해고, 1일차·0점·목표 200점 일반 진행을 파일과 Waiting에서 복원했다. 준비 1개·읽기 4개 모두 통과했다. |
| UI 배치 | 480×854, 320×568, 854×480 패널 크기에서 평가 본문·두 줄 오류 안내의 넘침이 없고 재시도 버튼이 영역 안에 있었다. 주 입력과 재시도의 영역이 겹치지 않는지, 해고 저장 재시도 완료 후 같은 위치의 다음 클릭이 다시 시작 버튼에 닿지 않는지도 실제 레이캐스트로 확인했다. 실제 기기 해상도·회전 검증을 대신하지 않는다. |
| 기존 결과·Start | `MissionResultTests` 15개, 실제 GamePlay 결과·저장 8개, 기존 Start 진입 4개 모두 통과했다. |
| 기존 차량·조향 | 62개 중 53개 통과·9개 기존 실패. 이전 단계와 실패 이름이 동일하며 기존 교통 차량 질량의 1.2배 계수와 기대값 차이는 수정하지 않았다. |
| WebGL C# 분기 | Unity 참조와 WebGL 정의를 사용한 컴파일에서 오류 0·경고 0. 실제 IL2CPP·브라우저 빌드는 아니다. |

이번 단계의 신규 검증 항목 17개는 모두 통과했다. 이전 단계 검증 89개를 함께 보면 중복 실행을 제외한 총 106개 중 97개 통과·9개 기존 실패다. 새 컴파일 오류·NullReferenceException·MissingReferenceException·폰트 글리프 누락은 관찰되지 않았다. 의도한 저장 오류·손상 읽기 경고와 기존 Unity 라이선스·종료 진단은 로그에 남아 있다.

연속 평가 검증은 중간 6~9일차·11~14일차를 실제 `TryCompleteDay`·저장 API로 단축하고 각 구간 마지막 날은 실제 GamePlay 결과 확인 경로를 사용했다. 결과 HP·후송 단계는 해당 검증에서 주입했다. 15개 미션 전체를 실제 운전·픽업으로 완주한 검증으로 해석하지 않는다.

영구 추가 테스트는 `Assets/Scripts/Editor/WaitingProgressTests.cs`와 메타다. 기존 `MissionResultTests.cs`는 유지하고, 삭제된 `PerformanceRulesTests.cs`·`ProgressStoreTests.cs`·`MissionPerformanceTests.cs`와 메타는 복원하지 않았다. 연속 평가·프로세스 재실행용 소스는 검증 복사본에만 두고 결과 XML·로그는 `.utmp/PerformanceStage5/`에 기록했다.

## 변경 범위와 미검증

기존 Assets·Packages·ProjectSettings의 SHA-256 비교에서 변경된 기존 파일은 `Waiting.unity`와 `WaitingMissionController.cs` 2개뿐이다. 새 테스트와 메타를 추가했으며 기존 메타·진행 모델·저장 형식·패키지·프로젝트 설정·Start·GamePlay 씬·충돌 물리는 유지했다.

실제 WebGL·모바일 브라우저의 빌드·저장 권한·페이지 재실행 영속성과 육안 렌더링은 미검증이다. 백그라운드에서 요청 타이머를 멈추는 처리도 아직 구현하지 않았다.

수동 확인은 5일차 결과 확인→6일차 평가→계속하기→동일 일차의 새 목표 안내 순서다. 미달이면 해고 화면에서 별도 다시 시작을 눌러 1일차·0점·목표 200점이 되는지 확인한다. 자동 검증과 달리 실제 주행 전체의 밸런스는 추후 수치 조정과 기기 검증이 필요하다.
