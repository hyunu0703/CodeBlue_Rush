# 스크립트 작성 규칙

## 1. 최우선 원칙

코드 작성 우선순위는 다음과 같다.

**정상 동작  
→ 책임과 구조  
→ 안정성  
→ 가독성  
→ 자료구조  
→ 성능  
→ 중복 제거  
→ 코드량 감소**

가장 짧은 코드가 아니라

**필요한 기능을 가장 단순하고 안전하며 효율적으로 표현하는 코드**

를 작성한다.

---

## 2. 코드 작성 전 설계

새 기능을 바로 코드로 작성하지 않는다.

**요구사항 분석  
→ 기존 시스템 확인  
→ 기능 위치 결정  
→ 클래스 책임 결정  
→ 데이터 소유권 결정  
→ 확장 가능성 확인  
→ Interface / 상속 / 컴포지션 판단  
→ 데이터 흐름 결정  
→ 자료구조 선택  
→ 실행 빈도 확인  
→ 시간 복잡도 확인  
→ 구현**

기존 시스템으로 해결할 수 있다면 같은 역할의 시스템을 새로 만들지 않는다.

---

## 3. 이름 규칙

클래스명, 함수명, 변수명은

**의미가 유지되는 범위에서 가장 짧게**

작성한다.

```csharp
int hp;
int damage;
void TakeDamage()
```

불필요하게 긴 이름은 피한다.

```csharp
int currentPlayerCharacterHealthPointValue;
```

하지만 짧게 만들기 위해 의미를 없애지 않는다.

```csharp
int a;
int tmp2;
```

---

## 4. 선언부 한 줄 규칙

변수 선언은 한 줄로 작성한다.

```csharp
[SerializeField] private BattleSystem battleSystem;
```

함수 선언도 한 줄을 기본으로 한다.

```csharp
private void Attack(Unit attacker, Unit target, SkillData skill)
```

매개변수를 여러 줄로 나열하지 않는다.

단, 함수 선언이 지나치게 길어진다면 줄바꿈보다 먼저

**함수 책임이 너무 많은지  
매개변수가 너무 많은지**

검토한다.

---

## 5. 긴 로직 작성

함수 내부까지 한 줄로 압축하지 않는다.

실행 흐름이

**위 → 아래**

순서로 자연스럽게 읽히도록 작성한다.

```csharp
int damage = CalcDamage(attacker, target, skill);

target.TakeDamage(damage);

CheckDead(target);
```

---

## 6. 함수 하나 = 역할 하나

함수는 가능한 하나의 역할만 담당한다.

```text
CalcDamage
TakeDamage
CheckDead
```

하나의 함수가

데미지 계산  
HP 변경  
UI 변경  
사망 처리  
보상 지급

을 전부 담당하지 않게 한다.

단, 의미 없는 작은 함수로 과도하게 쪼개지 않는다.

---

## 7. 클래스 하나 = 주요 책임 하나

가능하면 하나의 클래스는 하나의 주요 책임을 가진다.

```text
BattleFlow
→ 전투 흐름 관리

DamageCalculator
→ 데미지 계산

BattleUnit
→ 전투 상태 관리
```

단순한 기능을 억지로 여러 클래스로 분리하지 않는다.

---

## 8. 데이터의 주인은 하나

하나의 상태값을 여러 클래스가 직접 수정하지 않는다.

HP를 `BattleUnit`이 관리한다면

```csharp
unit.TakeDamage(damage);
```

처럼 요청한다.

외부 클래스가 직접

```csharp
unit.Hp -= damage;
```

처럼 수정하지 않는다.

---

## 9. 데이터 변경 경로 제한

외부에서 읽기만 필요한 값은 읽기 전용으로 제공한다.

```csharp
public int Hp => hp;
```

외부에서 변경해야 할 이유가 없다면 setter를 공개하지 않는다.

---

## 10. 접근 제한자

기본은 `private`를 우선한다.

Inspector 연결이 필요하면

```csharp
[SerializeField] private BattleSystem battleSystem;
```

을 사용한다.

정말 외부 접근이 필요한 경우에만 `public`을 사용한다.

---

## 11. 불필요한 코드 제거

사용하지 않는 다음 요소는 제거한다.

- 변수
- 함수
- `using`
- 클래스
- Interface
- public
- 주석
- 빈 줄
- 중복 코드
- Debug.Log

목표는 코드 줄 수가 아니라

**불필요한 코드량 제거**

이다.

---

## 12. 중복 코드

같은 책임과 같은 변경 이유를 가진 중복 코드는 한 곳으로 합친다.

현재 코드가 우연히 같다는 이유만으로 무조건 공통화하지 않는다.

---

## 13. Update 최소화

매 프레임 실행할 필요가 없는 기능에는 `Update`를 사용하지 않는다.

가능하면

**Event  
입력 이벤트  
상태 변경 시 함수 호출**

방식을 사용한다.

---

## 14. Update / FixedUpdate / LateUpdate 구분

**Update**  
일반 게임 로직, 입력

**FixedUpdate**  
물리 기반 처리

**LateUpdate**  
다른 객체 갱신 이후 처리

목적에 맞는 생명주기를 사용한다.

---

## 15. 반복 검색 금지

자주 실행되는 코드에서 다음을 반복하지 않는다.

```text
Find
FindObject 계열
GetComponent 반복
전체 List 반복 검색
같은 계산
```

필요한 값은 캐시해서 재사용한다.

---

## 16. GetComponent 기준

`GetComponent` 자체를 금지하지 않는다.

초기화 시 한 번 가져오는 것은 정상적인 사용이다.

```csharp
private Rigidbody2D rb;

private void Awake()
{
    rb = GetComponent<Rigidbody2D>();
}
```

문제는 매 프레임 반복하는 것이다.

---

## 17. 필수 Component 보장

반드시 필요한 Component가 있다면 `RequireComponent` 사용을 검토한다.

```csharp
[RequireComponent(typeof(Rigidbody2D))]
public class PlayerMove : MonoBehaviour
```

가능한 경우 잘못된 설정 자체가 만들어지지 않도록 한다.

---

## 18. 자료구조 선택

가장 자주 수행하는 작업을 기준으로 선택한다.

**Array / List**  
순차 데이터, 인덱스 접근

**Dictionary**  
Key 검색

**HashSet**  
중복 방지, 존재 확인

**Queue**  
먼저 들어온 데이터부터 처리

**Stack**  
최근 데이터부터 처리

**Tree**  
계층 구조

**Graph**  
객체 간 연결 관계

---

## 19. 자료가 적다면 단순하게

데이터가 매우 적거나 한 번만 사용하는 기능에

Dictionary  
HashSet  
복잡한 구조

를 억지로 적용하지 않는다.

---

## 20. 시간 복잡도

자주 실행되는 게임 로직은 가능하면

**O(1)  
→ O(log n)  
→ O(n)**

순서로 더 좋은 방법을 검토한다.

하지만 이것을 절대 규칙으로 사용하지 않는다.

---

## 21. 시간 복잡도 판단 기준

항상 다음 세 가지를 함께 본다.

**시간 복잡도  
× 데이터 크기  
× 실행 빈도**

작은 데이터를 한 번 처리하는 `O(n²)`은 문제가 없을 수 있다.

반대로 큰 데이터를 매 프레임 처리하는 `O(n)`은 문제가 될 수 있다.

---

## 22. O(n log n) 허용

정렬  
초기화  
에디터 작업  
드물게 실행되는 처리

등 실제로 필요한 경우 `O(n log n)` 사용을 허용한다.

---

## 23. 중첩 반복

중첩 반복이 생기면

Dictionary  
HashSet  
사전 계산  
캐싱

으로 줄일 수 있는지 먼저 검토한다.

하지만 작은 데이터까지 복잡하게 만들지 않는다.

---

## 24. 반복 계산 금지

같은 결과를 반복해서 계산하지 않는다.

```csharp
int damage = CalcDamage();
```

필요한 곳에서 결과를 재사용한다.

---

## 25. GC 할당 관리

자주 실행되는 코드에서는 불필요한 메모리 할당을 줄인다.

주의 대상:

```text
new
LINQ
문자열 생성
List 생성
배열 생성
람다 캡처
```

특히 `Update`, AI, 전투 반복 로직에서 확인한다.

---

## 26. LINQ 사용 기준

LINQ를 무조건 금지하지 않는다.

실행 빈도가 낮고 가독성이 크게 좋아진다면 사용할 수 있다.

성능 민감한 반복 로직에서는 일반 반복문과 캐시 사용을 우선 검토한다.

---

## 27. Instantiate / Destroy

객체 생성과 삭제가 매우 자주 반복되면 Object Pooling을 검토한다.

몇 번만 생성되는 객체까지 Pooling하지 않는다.

---

## 28. Unity 초기화 순서

일반적인 역할은 다음처럼 사용한다.

**Awake**  
자기 자신의 참조와 초기 상태 준비

**OnEnable**  
이벤트 구독

**Start**  
초기화 이후 실행할 로직

**OnDisable**  
이벤트 해제

단, 여러 GameObject의 `Awake`, `OnEnable`, `Start` 호출 순서를 믿고 시스템을 설계하지 않는다.

---

## 29. 초기화 의존성

다른 클래스의 초기화 완료가 반드시 필요하다면

Unity 호출 순서를 기대하지 않는다.

필요한 경우 명시적으로

```csharp
Init()
```

같은 초기화 함수를 사용한다.

---

## 30. 이벤트 규칙

이벤트는 중복 구독되지 않게 한다.

```csharp
private void OnEnable()
{
    gameEvent += HandleEvent;
}

private void OnDisable()
{
    gameEvent -= HandleEvent;
}
```

항상 다음을 확인한다.

**중복 구독  
해제 누락  
파괴된 객체 호출**

---

## 31. Coroutine 규칙

Coroutine 실행 전에 다음을 확인한다.

**이미 실행 중인지  
중복 실행 가능한지  
정상 종료 조건이 있는지  
객체 파괴 시 안전한지**

불필요한 Coroutine은 사용하지 않는다.

---

## 32. null 안정성

항상 다음 가능성을 확인한다.

**Inspector 연결 누락  
Component 누락  
ScriptableObject 미연결  
빈 배열/List  
파괴된 객체 참조  
초기화 이전 접근**

필요하면 빠르게 종료한다.

```csharp
if (target == null)
    return;
```

---

## 33. 잘못된 상태 방지

잘못된 값이 들어온 뒤 처리하는 것보다

**잘못된 값 자체가 들어오지 못하도록**

설계한다.

```csharp
[SerializeField, Min(1)] private int maxHp = 100;
```

Inspector 제한  
입력값 검증  
생성 시 검증

을 활용한다.

---

## 34. 직렬화 데이터 보호

Scene  
Prefab  
ScriptableObject

에서 사용 중인 `[SerializeField]`를 수정할 때 기존 데이터 유실 가능성을 확인한다.

필드명을 변경해야 한다면 필요 시

```csharp
[FormerlySerializedAs("oldHp")]
[SerializeField] private int hp;
```

를 사용한다.

---

## 35. 리소스 소유권

생성하거나 획득한 리소스는 누가 해제할지 명확해야 한다.

예:

```text
이벤트 구독 → 해제
Coroutine → 종료 관리
NativeArray → Dispose
Pool 객체 → 반환
임시 리소스 → 해제
```

**소유자 = 정리 책임자**

원칙을 따른다.

---

## 36. Interface 사용 기준

서로 다른 객체가 같은 행동 규칙을 가져야 할 때 Interface를 검토한다.

구현체가 하나뿐이거나 확장 가능성이 낮다면 만들지 않는다.

---

## 37. 상속보다 컴포지션 우선 검토

기능을 조합할 수 있다면 컴포지션을 먼저 검토한다.

상속이 실제 부모-자식 관계를 표현할 때만 사용한다.

긴 상속 체인은 피한다.

---

## 38. 테스트 가능한 구조

계산과 게임 규칙은 가능한 한 Unity Scene이나 `MonoBehaviour`에 과도하게 묶지 않는다.

예:

```csharp
private int CalcDamage(...)
```

순수 계산은 별도 Scene 없이도 확인 가능한 구조를 우선한다.

---

## 39. Profiler 기반 최적화

성능 문제를 감으로 판단하지 않는다.

순서는 다음과 같다.

**측정  
→ 병목 확인  
→ 원인 분석  
→ 최적화  
→ 다시 측정**

실제 문제가 없는 곳을 복잡하게 최적화하지 않는다.

---

## 40. Debug.Log 관리

개발 중 필요한 로그는 사용한다.

최종 코드에서는 불필요한 로그를 제거한다.

특히 다음 위치의 반복 로그를 주의한다.

```text
Update
FixedUpdate
반복문
AI 반복 처리
```

---

## 41. 코드 압축 기준

줄 수를 줄이기 위해 코드를 읽기 어렵게 만들지 않는다.

피함:

```csharp
if (target != null && skill != null && target.Hp > 0) target.TakeDamage(CalcDamage());
```

권장:

```csharp
if (target == null || skill == null)
    return;

if (target.Hp <= 0)
    return;

target.TakeDamage(CalcDamage());
```

목표는

**최소 줄 수가 아니라 최소 복잡도**

이다.

---

# 주석 규칙

## 42. 클래스 주석

스크립트 클래스 바로 위에 `/// <summary>`를 작성한다.

```csharp
/// <summary>전투 흐름을 관리한다.</summary>
public class BattleFlow : MonoBehaviour
```

---

## 43. 함수 주석

각 함수 바로 위에 함수 역할을 짧게 작성한다.

```csharp
// 한 턴의 전투를 진행한다
private void RunTurn()
```

---

## 44. 함수 내부 주석

모든 코드에 주석을 붙이지 않는다.

다음 경우에만 작성한다.

**중요한 상태 변경  
데이터 흐름 핵심  
코드만으로 의도를 알기 어려운 부분**

---

## 45. 주석 문체

실제 코드 실행을 설명할 때는

**`~한다`**

로 끝낸다.

마침표는 사용하지 않는다.

```csharp
// 데미지를 계산한다
// 대상의 HP를 감소한다
// 다음 턴을 시작한다
```

---

## 46. 명사형 주석

`~한다`가 자연스럽지 않다면

**~함  
~음  
명사형**

을 사용한다.

단순 명사보다 역할이 드러나는 표현을 우선한다.

```csharp
// 중복 실행 방지
// 이벤트 구독 해제
// 전투 상태 관리
// 캐릭터 데이터 확인
```

피함:

```csharp
// 상태
// 이벤트
// 데이터
```

주석 끝에는 마침표를 사용하지 않는다.

---

# 기존 코드 수정 규칙

## 47. 기존 코드부터 분석

기존 스크립트가 있다면 바로 전체를 다시 작성하지 않는다.

먼저 확인한다.

**클래스 책임  
잘된 부분  
문제점  
다른 클래스 연결  
유지해야 할 API**

---

## 48. 최소 변경 우선

가능하면 기존 구조를 유지하면서 최소한의 변경으로 해결한다.

구조 자체가 잘못된 경우에만 리팩터링한다.

---

## 49. 새 시스템 중복 금지

이미 같은 책임을 가진 시스템이 있다면 새 클래스를 만들지 않는다.

기존 시스템 확장이 더 자연스러운지 먼저 확인한다.

---

## 50. 과도한 설계 금지

미래에 사용할 수도 있다는 이유만으로

Manager  
Interface  
BaseClass  
Service  
Factory

등을 미리 만들지 않는다.

현재 요구사항과 가까운 확장 가능성까지만 고려한다.

---

# 팀 개발 규칙

## 53. 공개 API 변경 주의

다른 클래스가 사용하는

public 함수  
프로퍼티  
이벤트  
Interface

를 변경할 때 영향을 받는 코드를 먼저 확인한다.

---

## 54. Inspector 연결 변경 주의

기존 Scene과 Prefab에서 사용하는 참조를 변경하거나 제거할 때

기존 연결이 끊기지 않는지 확인한다.

---

# 최종 최적화 규칙

## 55. 구현 후 반드시 다시 줄인다

기능 구현 후 다음을 다시 확인한다.

**스크립트 수를 줄일 수 있는가  
함수를 줄일 수 있는가  
변수를 줄일 수 있는가  
중복을 제거할 수 있는가  
반복 검색을 제거할 수 있는가  
연산량을 줄일 수 있는가  
더 적합한 자료구조가 있는가**

가독성이 나빠진다면 줄이지 않는다.

---

## 56. 마지막 기준

마지막으로 항상 질문한다.

**“기능과 가독성을 유지하면서 코드와 연산량을 더 줄일 수 있는가?”**
