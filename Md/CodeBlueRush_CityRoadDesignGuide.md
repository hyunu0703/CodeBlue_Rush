# CodeBlueRush 도시 도로·보도 설계 가이드 — Maps.png 최우선 개정판

> 기준 프로젝트: Unity 6000.3.23f1 / 2D / WebGL / 모바일 / 480×854
>
> 최우선 참고 이미지: `Assets/Image/Maps/Reference/Maps.png`
>
> 현재 제작 방향: 도시 리소스와 `NewGamePlay` Scene의 시각 배치를 먼저 완성하고, Navigation / Lane / AI / Traffic System은 이후 단계에서 연결한다.
>
> **설계 우선순위: Maps.png 구조 재현 → 도로·보도 연결성 → 게임플레이 가독성 → 리소스 재사용/최적화**
>
> 최종 웹사이트 100 MB 제한은 유지한다. 단, 용량을 줄이기 위해 Maps.png의 핵심 도로 위치·연결·교차로·다리·보도 구조를 임의로 삭제하거나 바꾸지 않는다.

---

# 1. 문서 목적

이 문서는 `Maps.png`의 도시 도로와 보도 구조를 Unity에서 재현하기 위한 기준이다.

이 문서가 담당하는 범위:

- 외곽 순환도로
- 내부 직선도로
- 코너 도로
- T자 도로
- 십자 교차로
- 다리와 하천 횡단부
- 병원 내부 원형 진입부
- 주차장/시설 진입도로
- 중앙 녹지대와 교통섬
- 횡단보도
- Sidewalk
- 해안·항만과 접하는 도로 경계
- 이후 Lane / Navigation을 얹을 수 있는 시각적 기준

이 문서가 현재 직접 구현하지 않는 범위:

- 차량 AI
- 시민 AI
- 신호 제어 로직
- Navigation 경로 탐색
- Lane Change
- 미션 로직

시스템 구현은 도로와 보도 배치가 확정된 뒤 별도 로직 레이어에 연결한다.

---

# 2. 최우선 기준과 문서 연결

기준이 충돌할 때 다음 순서를 사용한다.

```text
1. Maps.png의 실제 위치 관계와 연결 구조
↓
2. CodeBlueRush_CityRoadDesignGuide.md의 도로/보도 구현 규칙
↓
3. CodeBlueRush_BuildingPlacementGuide.md의 블록/건물 배치 규칙
↓
4. CodeBlueRush_MapAssetStyleGuide.md의 시각 스타일 규칙
↓
5. 최적화 방식
```

중요:

- `Maps.png`가 도로 위치와 연결 구조의 Source of Truth다.
- 문서에 임의의 도로 개수나 비율이 적혀 있더라도 `Maps.png`와 다르면 `Maps.png`를 따른다.
- 최적화는 **같은 구조를 더 적은 리소스로 표현하는 방식**으로 해결한다.
- 최적화를 이유로 도로망 자체를 단순화하지 않는다.

---

# 3. Maps.png에서 반드시 유지할 도시 골격

## 3.1 외곽 순환도로

도시 전체를 감싸는 연속된 외곽 도로가 있다.

특징:

- 상단 가로도로
- 좌측 세로도로
- 우측 세로도로
- 하단 해안과 나란한 가로도로
- 네 모서리의 큰 90° 곡선
- 내부 도로와 여러 지점에서 연결

외곽 순환도로는 끊기면 안 된다.

Maps.png에서 가장 큰 도로 골격이므로 내부 블록보다 먼저 배치한다.

---

## 3.2 내부 도로는 직교형 Grid가 중심

Maps.png의 내부 도로는 대부분 다음 구조다.

- 수평 직선
- 수직 직선
- T자 연결
- 십자 연결
- 짧은 시설 진입부

주거지역이나 공원이라고 해서 공공 도로 자체가 과도하게 굽어 있지 않다.

곡선은 주로:

- 외곽 순환도로 모서리
- 병원 원형 진입부
- 시설 내부 차량 동선

에 사용한다.

따라서 기존처럼 구역별로 `커브 약 8`, `커브 약 9`와 같은 임의 개수를 먼저 정하지 않는다.

---

## 3.3 중앙 하천 축

Maps.png 중앙에는 북쪽에서 남쪽으로 이어지는 하천이 있다.

특징:

- 도시를 좌우로 나누는 강한 시각적 축
- 하천 양쪽에 도로와 블록이 배치됨
- 여러 위치에서 다리로 연결됨
- 중·하단은 공원과 자연 지형이 넓어짐
- 하단 해안 수역으로 이어짐

하천의 위치와 폭, 굽이, 다리 위치는 `Maps.png`를 그대로 기준으로 한다.

다리 개수를 임의로 추가하거나 삭제하지 않는다.

---

## 3.4 하단 해안과 항만

도시 하단은 넓은 수역과 맞닿아 있다.

반드시 표현할 요소:

- 하단 해안선
- 해안과 평행한 외곽도로
- 방파제/제방 성격의 구조물
- 좌측 하단 항만 수역
- 부두
- 컨테이너 크레인
- 선박

항만 수역과 중앙 하천은 서로 완전히 별개의 장식으로 보이지 않도록 전체 물 지형의 연결감을 유지한다.

---

# 4. Maps.png 기준 주요 지역과 도로 성격

구역은 도로 개수를 강제로 정하기 위한 것이 아니라 **Maps.png를 읽기 위한 위치 구분**이다.

| 지역 | 대략적 위치 | 도로 특징 |
| --- | --- | --- |
| 주거 블록 | 좌측 상단 | 직선 Grid, 작은 블록, 보도 밀도 높음 |
| 상업·업무 블록 | 중앙 상단 | 직선 Grid, 교차로 많음, 블록 간 연결 촘촘함 |
| 병원 캠퍼스 | 우측 상단 | 외곽 Grid + 내부 진입로 + 원형 회차부 |
| 산업·항만 | 좌측 중·하단 | 큰 블록, 직선도로, 물류/부두 진입부 |
| 하천·공원 축 | 중앙 세로 | 하천 양측 도로, 다리, 공원 경계, 보행 경로 |
| 혼합 업무·공공 블록 | 우측 중앙 | 중형 블록, 주차장, 광장, 직선도로 |
| 소방서 구역 | 우측 하단 | 외곽도로 + 넓은 시설 진입부/차량 야드 |

기존의 “6개 구역” 개념은 큰 기능 구분으로 사용할 수 있지만, Maps.png에는 구역 사이의 혼합 블록도 있으므로 경계를 지나치게 딱 잘라 나누지 않는다.

---

# 5. 차선 기준

Maps.png에서 대부분의 공공 도로는 **한 방향 1개 차로씩 사용하는 양방향 도로**로 읽힌다.

따라서 기본 도로는 다음으로 통일한다.

```text
양방향 2차로 도로
= 반대 방향 1차로 + 1차로
```

기존 문서의 `2차선 40% / 4차선 60%` 같은 비율은 Maps.png에서 명확히 확인할 수 없으므로 고정 규칙으로 사용하지 않는다.

더 넓어 보이는 구간은:

- 도로 폭 자체 확대
- 시설 진입부
- 주차/회차 공간
- 녹지 중앙분리대

로 표현한다.

Maps.png에서 실제 4차로가 명확하게 확인되는 경우에만 별도 4차로 리소스를 추가한다.

---

# 6. 필수 도로 리소스 세트

최소 세트:

- `Road_Straight`
- `Road_Corner90`
- `Road_TJunction`
- `Road_Intersection4Way`
- `Road_Bridge`
- `Road_Entrance`
- `Road_Service`
- `Road_Roundabout`
- `Road_AsphaltBase`
- `RoadMarking_CenterLine`
- `RoadMarking_EdgeLine`
- `RoadMarking_Arrow`
- `Crosswalk`
- `Median_GreenStrip`
- `TrafficIsland`

방향별 PNG를 따로 만들지 않는다.

예:

```text
Road_TJunction
→ 0° / 90° / 180° / 270° 회전
```

# 7. 교차로 규칙

## 7.1 십자 교차로

Maps.png에서 내부 Grid의 주요 연결 형태다.

규칙:

- 네 방향 도로 폭이 자연스럽게 이어짐
- 중앙선이 교차로 중앙에서 부자연스럽게 겹치지 않음
- 횡단보도는 보도와 정확히 연결
- 코너 보도가 끊기지 않음

---

## 7.2 T자 도로

도로가 하천, 시설 블록, 공원, 큰 캠퍼스에서 끝날 때 사용한다.

규칙:

- 없는 방향으로 아스팔트가 뻗어 나가면 안 됨
- Sidewalk도 없는 도로 방향으로 잘못 이어지면 안 됨
- 횡단보도는 실제 연결된 접근로 기준으로 배치

---

## 7.3 코너 도로

Maps.png에서 공공 도로의 코너는 주로 외곽 순환도로에 사용한다.

특징:

- 넓은 곡률
- 자연스러운 중앙선 곡선
- 바깥쪽/안쪽 Sidewalk 연속
- 나무와 녹지 경계가 곡선을 따라감

내부 Grid에 불필요하게 코너를 추가하지 않는다.

---

# 8. 병원 원형 진입부

Maps.png 병원 하단에는 원형 회차부가 있다.

이 구조는 일반 교차로와 별도 취급한다.

구성:

```text
병원 진입도로
↓
원형 회차부
↓
병원 주차/시설 진입
```

필수:

- 중앙 녹지섬
- 원형 차량 동선
- 주변 Sidewalk
- 주차장 연결
- 병원 본관 접근 동선

공공 도로의 일반 Roundabout 시스템으로 확대 해석하지 말고 우선 Maps.png의 병원 캠퍼스 전용 구조로 재현한다.

---

# 9. 중앙 녹지대와 도로 사이 섬

Maps.png에는 일부 수평 도로 사이에 긴 녹지대가 배치되어 있다.

표현 방식:

```text
도로
+ 녹지 Strip / Tree Strip
+ 도로 또는 블록 경계
```

이를 새 도로 텍스처 한 장으로 만들지 않는다.

- 도로 Base 재사용
- `Median_GreenStrip`
- 나무/관목

조합으로 표현한다.

---

# 10. Sidewalk 절대 규칙

Maps.png 재현에서 Sidewalk는 도로 다음으로 중요한 구조다.

## 10.1 기본 연속성

- 일반 도로 양쪽에 Sidewalk를 둔다.
- 블록 외곽을 따라 끊기지 않게 연결한다.
- 교차로 코너에서도 Sidewalk가 이어져야 한다.
- 건물 배치 때문에 Sidewalk 위치를 이동하지 않는다.

---

## 10.2 교차로 Sidewalk

교차로에서는 다음 순서를 지킨다.

```text
Sidewalk
↓
연석/코너
↓
Crosswalk
↓
반대편 Sidewalk
```

Crosswalk가 잔디나 건물 벽으로 연결되면 실패다.

---

## 10.3 시설 진입부

병원, 소방서, 산업시설, 주차장 진입부에서는 Sidewalk가 진입로와 충돌하지 않도록 처리한다.

- Driveway 부분만 연속적으로 낮아지는 형태
- Sidewalk 전체를 삭제하지 않음
- 진입부 전후 보도 연결 유지

---

## 10.4 하천과 Sidewalk

하천을 따라 도로가 이어지는 구간:

- 도로 측 Sidewalk는 유지
- 하천 쪽은 공간에 따라 보도/녹지 경계 사용
- 공원 내부 산책로는 일반 Sidewalk와 구분

`Sidewalk`와 `ParkPath`를 같은 리소스로 처리하지 않는다.

---

# 11. Crosswalk 규칙

Maps.png에서는 대부분의 주요 교차로에서 횡단보도가 강하게 보인다.

따라서:

- 십자 교차로: Maps.png에 보이는 방향 수만큼 배치
- T자 교차로: 실제 접근 방향 기준
- 병원/시설 진입부: 참고 이미지에서 확인되는 경우만 추가
- 외곽 순환도로 연결부: 내부 보도와 이어지도록 배치

모든 교차로에 무조건 4개를 자동 배치하는 방식은 사용하지 않는다.

---

# 12. 하천 다리 규칙

다리는 도시 연결 구조를 결정하는 핵심 지점이다.

규칙:

- Maps.png의 상대 위치를 그대로 따른다.
- 다리 전후 도로 Center가 맞아야 한다.
- 좌우 Sidewalk 또는 보행 연결이 자연스럽게 이어져야 한다.
- 다리 아래 하천 Edge가 갑자기 끊기지 않아야 한다.
- 다리 때문에 하천 폭을 임의로 바꾸지 않는다.

다리의 시각 재질이 목재/석재처럼 보이더라도 차량 통행 여부는 실제 Maps.png 연결 구조와 게임 기획을 함께 확인한다.

시각만 보고 새로운 차량 경로를 임의로 만들지 않는다.

---

# 13. 항만·해안 도로 규칙

좌측 하단 산업·항만은 일반 도시 블록과 다르게 처리한다.

필수 연결:

- 산업 블록 외곽도로
- 창고/물류시설 진입부
- 부두 접근부
- 항만 수역 경계
- 하단 외곽도로

해안 쪽 도로는 물과 직접 붙지 않고 Maps.png처럼:

```text
도로
→ 보도/녹지/제방 구조
→ 바위/해안 경계
→ 물
```

의 단계가 보이도록 한다.

---

# 14. 도로 시각 레이어

권장 구조:

```text
Ground
↓
RoadBase
↓
RoadMarking
↓
Sidewalk
↓
```

큰 완성형 도로 PNG를 여러 장 만드는 것보다 조합형 리소스를 사용한다.

단, 조합 때문에 Maps.png의 교차로 모양이 달라지면 안 된다.

```text

↓
6. Maps.png와 다리 위치 비교
↓
7. 병원 원형 진입부/시설 진입부 배치
↓
8. Sidewalk 전체 연결
↓
9. Crosswalk 배치
↓
10. 녹지대/교통섬 배치
↓
11. 도로 연결 QA
↓
12. 통과 후 건물 배치 시작
```

건물은 11단계가 통과되기 전에 배치 기준을 확정하지 않는다.

# 17. 도로 연결 QA

## 17.1 외곽 도로

- [ ] 도시 전체를 한 바퀴 연속 주행할 수 있는가
- [ ] 네 모서리 곡선이 자연스럽게 연결되는가
- [ ] 하단 해안도로가 좌우 외곽도로와 연결되는가

## 17.2 내부 Grid

- [ ] 도로가 블록 중간에서 갑자기 끊기지 않는가
- [ ] T자 도로가 십자 도로로 잘못 표현되지 않았는가
- [ ] Maps.png에 없는 도로가 추가되지 않았는가
- [ ] Maps.png에 있는 도로가 누락되지 않았는가

- [ ] 다리 양쪽 도로가 정확히 연결되는가
- [ ] 하천 Edge가 다리 때문에 끊기지 않는가

# 18. Maps.png 대조 테스트

도로 파트 완료 후 Unity Scene을 탑뷰로 캡처하고 `Maps.png`와 나란히 비교한다.

비교 순서:

```text
1. 외곽 윤곽
2. 하천 위치
3. 큰 수평/수직 도로
4. 블록 크기
5. 교차로 형태
6. 다리 위치
7. Sidewalk
8. Crosswalk
```

장식과 건물이 없어도 위 8개가 유사하게 읽혀야 도로 파트를 통과한다.

---

# 19. 이후 시스템 연결 준비

시각 도로와 시스템 데이터는 분리한다.

```text
Visual
- RoadBase
- RoadMarking
- Sidewalk
- Crosswalk

Later Logic
- Lane
- Navigation Node
- CameraTurnZone
- Traffic Signal
- Vehicle Spawn
```

현재 리소스 배치 단계에서는 Logic 컴포넌트를 억지로 추가하지 않는다.

도로 위치가 확정된 뒤 해당 위치를 기준으로 Logic을 연결한다.

---

# 20. 리소스 최적화

Maps.png 구조를 유지한 상태에서 다음 순서로 최적화한다.

```text
1. 동일 Sprite 회전 재사용
2. Road Base / Marking 분리
3. Sidewalk 반복 타일화
4. Crosswalk/Arrow Overlay화
5. Atlas 적용
6. 불필요한 투명 여백 제거
7. Max Size 조정
8. Web 압축
```

금지:

- 용량 때문에 다리 삭제
- 용량 때문에 교차로 단순화
- 용량 때문에 외곽도로 일부 삭제
- Maps.png의 블록 구조를 줄여 버리기

# 21. WebGL 기술 Gate

최종 웹사이트 배포 용량은 100 MB를 초과하지 않는다.

권장:

- Development Build: Off
- Brotli Compression
- Read/Write: Off
- 고정 탑뷰 Sprite Mip Map: 기본 Off
- Sprite Atlas 사용
- 불필요한 방향별 중복 Texture 금지

현재 빌드 크기는 문서에 고정 숫자로 적지 않는다.

항상 작업 시점의 Release Build 결과를 기준으로 측정한다.

# 23. 최종 판단 원칙

```text
Maps.png에 도로가 있는가?
→ 있으면 같은 위치 관계와 연결로 구현한다.

Maps.png에 도로가 없는가?
→ 게임 시스템 때문에 꼭 필요한 경우가 아니면 추가하지 않는다.

용량이 큰가?
→ 구조를 삭제하지 말고 Sprite 재사용/압축/해상도로 해결한다.
```

**도로와 보도 구조에 대한 최종 기준은 항상 `Maps.png`다.**
